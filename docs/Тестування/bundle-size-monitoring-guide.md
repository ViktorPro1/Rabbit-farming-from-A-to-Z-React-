# Політика bundle-size: моніторинг і оптимізація

Коротка інструкція — як у подальшому перевіряти, чи бандл не "розповз" знову.

---

## Який файл відкривати

Після кожного `npm run build` у папці `dist/` з'являється файл:

```
dist/stats.html
```

Відкрийте його прямо в браузері (подвійний клік або `xdg-open dist/stats.html` у терміналі), або кнопкою Go Live у VSCodi. Це інтерактивна treemap-діаграма всього бандла: кожен прямокутник — модуль, розмір прямокутника відповідає його вазі у зібраному JS.

Файл генерується автоматично плагіном `rollup-plugin-visualizer`, який вже підключений у `vite.config.ts`. Нічого додатково вмикати не треба — він спрацьовує при кожному білді.

---

## Як швидко перевірити ситуацію

Не обов'язково щоразу відкривати `stats.html` — спершу гляньте вивід самого білда в терміналі:

```bash
npm run build
```

Наприкінці виводу Vite показує список усіх чанків з розмірами (gzip теж). Найшвидший спосіб побачити найважчі — відсортувати:

```bash
npm run build 2>&1 | grep -iE "kB" | sort -t' ' -k2 -h -r | head -20
```

Це виведе топ-20 найважчих файлів (JS, CSS, зображення разом) — перше, на що варто дивитись.

## На що звертати увагу

**Орієнтовні "здорові" розміри** (зафіксовані після оптимізації 2026-08-06, зберігайте в голові як базову лінію):

| Чанк                          | Норма                                     |
| ----------------------------- | ----------------------------------------- |
| `AppRoutes.js`                | ~110 kB                                   |
| `vendor-react.js`             | ~455 kB (бібліотека, майже не змінюється) |
| `vendor-supabase.js`          | ~194 kB (бібліотека)                      |
| `navMap.generated.js`         | ~23 kB                                    |
| `Assistant.js` (лінивий)      | ~11 kB                                    |
| `index.js` (головний вхідний) | ~75-150 kB                                |

Якщо після нових змін якийсь із **не-vendor** чанків (тобто не `vendor-react`/`vendor-supabase`, там зростання очікуване лише при оновленні бібліотек) виріс **більш ніж на ~30-40%** — це привід відкрити `dist/stats.html` і подивитись, що саме туди потрапило.

## Дві типові причини роздування, які вже траплялись у цьому проєкті

### 1. Нова сторінка/компонент імпортується не через `lazy()`

Усі сторінки в `src/routes/groups/*.ts` мають підключатись так:

```tsx
const SomePage = lazy(() => import("../../pages/SomePage/SomePage"));
```

а не напряму:

```tsx
import SomePage from "../../pages/SomePage/SomePage"; // ❌ не для сторінок
```

Виняток — лише щось, що реально має бути готовим миттєво при першому завантаженні (таких зараз немає жодного, навіть `Home` тепер лінивий).

**Як перевірити:**

```bash
grep -rn "^import.*from \"\.\./\.\./pages/" src/routes/groups/
```

Якщо в результаті є щось окрім службових імпортів типу `Auth` (він навмисно не лінивий, бо потрібен миттєво для гейтингу) — варто перевірити, чи не мало б це бути `lazy()`.

### 2. Компонент, що рендериться на кожній сторінці, тягне важкі дані напряму

Компоненти на кшталт `Breadcrumbs`, `RunningTicker`, `Header`, `Footer` рендеряться синхронно на **кожній** сторінці (не всередині `<Suspense>`/`lazy()`-роутів). Якщо такий компонент імпортує щось важке (великий масив даних, велику бібліотеку) — ця вага потрапляє в кожне перше завантаження сайту, незалежно від того, яку сторінку відкрив користувач.

**Приклад з цього проєкту:** `src/data/sectionCards/groups/*` (236KB з описами й ключовими словами для пошуку) — потрібен лише `Assistant` і `SectionCards` (обидва тепер ліниві), а `Breadcrumbs`/`RunningTicker` беруть легку версію з окремого файлу `src/data/navMap.generated.ts` (генерується скриптом `scripts/generate-nav-map.ts`, автоматично перед кожним білдом).

**Як перевірити:** знайти, які великі файли даних імпортуються поза лінивими сторінками:

```bash
grep -rln "import.*from.*data/" src/components/ src/App.tsx
```

Для кожного результату — перевірити (`du -sh` на джерело даних), чи компонент реально не-лінивий (рендериться завжди), і чи справді потребує повного обсягу даних, чи вистачить легкої підмножини.

## Якщо потрібно перегенерувати `navMap.generated.ts` вручну

Файл гітігнорений і генерується автоматично на етапі `npm run build`. Якщо потрібно оновити його окремо (наприклад, після зміни `src/data/sectionCards`), без повного білду:

```bash
npx tsx scripts/generate-nav-map.ts
```

---

## Періодичність

Немає потреби перевіряти це щотижня — досить робити швидку перевірку (`npm run build` + сортування виводу) після будь-якої зміни, що:

- додає нову велику сторінку чи компонент
- додає новий великий масив даних чи нову залежність (npm-пакет)
- чіпає `Breadcrumbs`, `RunningTicker`, `Header`, `Footer`, `App.tsx` — усе, що рендериться на кожній сторінці

Повний аналіз через `dist/stats.html` — коли швидка перевірка показала підозрілий стрибок і незрозуміло, звідки він узявся.
