# Адмін-панель: що де лежить

Папка `src/pages/Admin/`. Сторінка доступна лише адміністраторам (перевірка через таблицю `admins`). Маршрут `/admin`.

## Головне правило

- **Усе, що працює з базою (завантаження, збереження, видалення, листи), живе в `Admin.tsx`.**
- **Файли в `components/` лише показують дані й викликають функції, які їм передали.** Вони самі нічого не завантажують і не пишуть у базу.

Тому: змінюєш вигляд блоку, йдеш у `components/`. Змінюєш поведінку чи запити, йдеш в `Admin.tsx`.

## Файли

| Файл | Що в ньому |
| --- | --- |
| `Admin.tsx` | Головна сторінка (приблизно 650 рядків). Стани, усі запити до Supabase, обробники кнопок, підписка на онлайн-присутність, складання блоків у одну сторінку |
| `Admin.css` | Усі стилі адмінки (класи `admin-*`, `stats-*`, `access-*`, `code-*`, `docs-*`, `online-*`, `nps-*`) |
| `Admin.test.tsx` | 15 тестів сторінки (запити паралельно, помилки видалення, права доступу тощо) |
| `types.ts` | Спільні типи: `OnlineVisitor`, `UserDataUsage`, `LeadRow`, `NpsFeedbackRow`, `DeactivatedUser`, `TableStat`, `BackendStats`, `InviteCode`, `PlanType`, `RegisteredUser` |
| `formatBytes.ts` | Функція, що перетворює байти в текст «Б / КБ / МБ» |
| `components/` | Десять блоків сторінки і допоміжний компонент `UsageBar` |

Тип `Profile` (рядок з таблиці `profiles`) лишився в `Admin.tsx`, бо його використовує тільки `fetchUsers`.

## Що лежить усередині Admin.tsx

**Константи й налаштування**
- `adminSupabase` окремий клієнт Supabase лише для каналу присутності (щоб не змішувати сесію адміна з присутністю відвідувачів).
- `PRESENCE_CHANNEL` назва каналу присутності.
- `TABLE_LIST` перелік таблиць для лічильників у блоці статистики. Має збігатися з функцією `get_table_counts()` у базі.

**Функції завантаження** (кожна пише в свій стан)
- `fetchCodes` інвайт-коди
- `fetchUsers` зареєстровані користувачі (профілі плюс прив'язані коди)
- `fetchDeactivated` деактивовані користувачі
- `fetchLeads` заявки з лід-магніту
- `fetchNpsFeedback` відгуки NPS
- `fetchVizytkaDownloads` лічильник завантажень візитки
- `fetchStats` розмір бази, сховища, лічильники таблиць
- `fetchUserUsage` використання по користувачах

**Обробники дій**
- `handleSetPlanType` зміна типу плану. Тут же надсилаються листи: при переході на «Платний» йде лист про активацію і квитанція, при поверненні з «Платного» чи «Засновника» на «Пробний» лист про скасування. VIP завжди безстроковий і листів не надсилає
- `handleSetAccessUntil`, `handleGrantOneMonth`, `handleMakeUnlimited` зміна терміну доступу
- `handleAdd`, `handleDelete`, `generateCode` інвайт-коди
- `handleDeleteUser` видалення профілю, потім звільнення інвайт-коду
- `handleRestoreUser` відновлення деактивованого користувача

**Ефекти**
- Перший `useEffect`: перевірка, чи користувач адмін, і одноразове завантаження всіх даних (незалежні запити йдуть паралельно).
- Другий `useEffect`: підписка на канал онлайн-присутності.

## Блоки сторінки (components/)

Порядок збігається з порядком на сторінці.

| Компонент | Що показує | Пропси | Дані беруться з |
| --- | --- | --- | --- |
| `OnlineVisitorsSection` | Хто зараз онлайн у довіднику | `visitors` | канал присутності |
| `BackendStatsSection` | Бази, користувачі, сховище, Bandwidth, акордеон з лічильниками таблиць | `stats`, `loading` | `fetchStats` |
| `UserUsageSection` | Використання диска по користувачах | `usage`, `loading` | `fetchUserUsage` |
| `VizytkaSection` | Скільки разів завантажили візитку | `downloads` | `fetchVizytkaDownloads` |
| `NpsSection` | Середня оцінка, NPS-індекс, таблиця відгуків (обчислення всередині) | `feedback`, `loading` | `fetchNpsFeedback` |
| `LeadsSection` | Таблиця лідів | `leads` | `fetchLeads` |
| `RegisteredUsersSection` | Користувачі, тип плану, термін доступу, видалення | `users`, `currentUserId` і п'ять функцій-дій | `fetchUsers` |
| `DeactivatedUsersSection` | Деактивовані користувачі з кнопкою «Відновити» (сам ховається, якщо список порожній) | `users`, `onRestore` | `fetchDeactivated` |
| `InviteCodesSection` | Лічильники кодів, додавання, генерація, таблиця, видалення | `codes`, `stats`, `newCode`, `error` і чотири функції-дії | `fetchCodes`, `fetchStats` |
| `DocsSection` | Статична довідка про email-сповіщення | немає | текст у самому файлі |
| `UsageBar` | Кольорова смужка заповнення (зелена, жовта від 70%, червона від 90%) | `used`, `total`, `label`, `color` | використовується в `BackendStatsSection` |

## Типові зміни: куди йти

| Що треба зробити | Де змінити |
| --- | --- |
| Змінити ліміти Supabase (500 МБ, 1 ГБ, 50 000 MAU) | Константи вгорі `components/BackendStatsSection.tsx`. Підписи «ліміт 500 МБ» і «ліміт 1 ГБ» у розмітці того ж файлу написані текстом, їх теж поправ |
| Додати таблицю в лічильники статистики | `TABLE_LIST` в `Admin.tsx` і функція `get_table_counts()` у базі (обидва місця мають збігатися) |
| Змінити текст довідки про листи | `components/DocsSection.tsx` |
| Додати новий тип плану | `PlanType` у `types.ts`, пункти `<option>` в `RegisteredUsersSection.tsx`, логіка в `handleSetPlanType`, обмеження в базі, текст у `DocsSection.tsx` |
| Змінити колонки таблиці користувачів | `components/RegisteredUsersSection.tsx` (і поля в `RegisteredUser` у `types.ts`, якщо додаєш нове поле) |
| Змінити, які листи надсилаються | `handleSetPlanType` в `Admin.tsx` |
| Змінити стилі | `Admin.css` |
| Додати новий блок на сторінку | Створи компонент у `components/`, тип додай у `types.ts`, функцію завантаження і стан додай в `Admin.tsx`, вставку компонента додай у кінець розмітки перед `DocsSection`. Додай тест в `Admin.test.tsx` |

## Відомі особливості

- `handleDeleteUser` спершу видаляє профіль, потім намагається звільнити інвайт-код. Якщо для таблиці `invite_codes` немає політики UPDATE для адміністраторів (RLS), код лишиться використаним, і адмін побачить про це повідомлення.
- Помилки завантаження й дій показуються угорі сторінки (`pageError`), помилки з інвайт-кодами біля самого блоку (`error`).
- Перевіряючи зміни вручну, не перемикай тип плану на «Платний» у справжніх користувачів: це надсилає реальні листи.
