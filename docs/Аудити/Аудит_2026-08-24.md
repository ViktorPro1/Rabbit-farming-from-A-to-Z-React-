## 3. Що реально реалізовано

### Архітектура

- React-застосунок запускається через `createRoot` у `src/main.tsx`.
- Використано `StrictMode` і `HelmetProvider`.
- Маршрути зібрані у 13 файлах у `src/routes` та групах маршрутів.
- Публічні й захищені маршрути формуються окремими route-групами.
- Сторінки та частина компонентів завантажуються через `lazy`/`Suspense`.
- Для невідомих маршрутів є окрема 404-сторінка.
- Є `ErrorBoundary` на рівні застосунку та окремо для Assistant.

### Дані та backend

- Клієнт Supabase створюється в `src/lib/supabase.ts`.
- Для клієнта потрібні `VITE_SUPABASE_URL` і `VITE_SUPABASE_ANON_KEY`; відсутність змінних завершує ініціалізацію помилкою.
- У `api/send-push.ts` використовується серверний `SUPABASE_SERVICE_ROLE_KEY`, а доступ до endpoint захищений заголовком `x-push-secret`.
- У `api/daily-reminders.ts` реалізовані нагадування для злучок, окролів, маточника, відлучення, забою, лікування та вакцинації.
- Для push використовується `web-push` з VAPID.

### PWA і SEO

- У Vite налаштовано `vite-plugin-pwa` зі стратегією `injectManifest`.
- `src/sw.ts` кешує precache, обробляє навігацію, push і кліки по сповіщеннях.
- Є manifest, іконки, shortcuts і screenshots у конфігурації Vite.
- Production build генерує sitemap і prerendered routes.
- У Vercel налаштовані SPA rewrite та заголовки CSP, HSTS у конфігурації не виявлено.

### Якість і тестування

- ESLint проходить без помилок.
- TypeScript build проходить без помилок.
- Unit-тести використовують Vitest і Testing Library.
- E2E-тести перевіряють публічні маршрути, 404, захищені маршрути без сесії, service worker, manifest і offline-банер.
- ErrorBoundary, App, CookieConsent, WelcomePopup, `usePublicPresence` і Supabase-модуль мають тестове покриття.
- Поточний coverage:

| Метрика | Результат |
|---|---:|
| Statements | 90.16% (165/183) |
| Branches | 82.85% (58/70) |
| Functions | 85.45% (47/55) |
| Lines | 90.79% (148/163) |

### CI/CD

- GitHub Actions окремо запускає lint, typecheck, tests і build.
- Build залежить від успішних lint, typecheck і tests.
- E2E job запускається тільки для `pull_request`.
- CI використовує Node 20 та `npm ci`.
- У build передаються Supabase environment variables через GitHub Secrets.

## 4. Підтверджені сильні сторони

1. **Базова інженерна перевірка зелена.** Lint, typecheck, unit-тести та production build проходять.
2. **Добре розділені маршрути.** Великі сторінки lazy-loaded, а route-групи розділяють домени застосунку.
3. **Є захист від падіння UI.** ErrorBoundary інтегрований і має власні тести.
4. **PWA не лише заявлена.** Build створює service worker, а E2E перевіряє його реєстрацію, manifest і offline-поведінку.
5. **Високе виміряне coverage для протестованого коду.** Це фактичний результат поточного `test:coverage`, а не число з README.
6. **Секрети backend відокремлені від клієнта.** Service role key використовується тільки в `api`-файлах, не в `VITE_*` клієнтському коді.

## 5. Підтверджені прогалини та ризики

### Високий пріоритет: вразливі production-залежності

`npm audit --omit=dev` повідомив про **2 high severity vulnerabilities** у `react-router` через `react-router-dom@7.18.1`. Audit вказує на RSC Mode CSRF bypass і доступне виправлення через `npm audit fix`.

Це не доводить експлуатацію саме в цьому застосунку, але залежність ідентифікована package manager як вразлива. Потрібно оновити сумісну версію, після цього повторити `npm audit`, lint, typecheck, unit-тести та build.

### Середній пріоритет: помилки Supabase у daily reminders не обробляються повністю

У `api/daily-reminders.ts` результати багатьох `.select()` деструктуруються лише як `{ data }`. Поле `error` не перевіряється. При збої запиту функція може продовжити роботу з порожнім результатом і завершитися HTTP 200 з неповним `sent`, тобто помилка не буде явно видима виклику.

Окремо, видалення протермінованої push-підписки всередині `sendToUser` також не перевіряє помилку Supabase. Це не доводить втрату даних, але ускладнює діагностику та повторну обробку.

### Середній пріоритет: E2E не запускаються на push у `main`

У `.github/workflows/ci.yml` E2E job має умову `github.event_name == 'pull_request'`. Отже, для push у `main` CI перевіряє lint, typecheck, unit-тести й build, але не запускає Playwright. Регресія production routing/PWA після merge може пройти CI.

### Середній пріоритет: E2E покривають лише Chromium desktop

У `playwright.config.ts` активний тільки проєкт Chromium Desktop Chrome. Mobile Chrome закоментований, Firefox і WebKit відсутні. Це не помилка конфігурації, але mobile UI, інші браузери та частина PWA-поведінки тестами не підтверджені.

### Низький пріоритет: документація розходиться з кодом

- README має застарілі кількісні показники порівняно з поточним деревом і test run.
- Попередні аудити містять твердження про відсутній ErrorBoundary, але він реально є в `src/components/ErrorBoundary/ErrorBoundary.tsx` і покритий тестами.
- Частина старих рекомендацій в аудиторських документах описує вже виправлені стани. Це створює ризик прийняття неправильних рішень за старим звітом.

### Низький пріоритет: відсутні локальні міграції Supabase

У поточному дереві не знайдено `supabase`-папки або файлів міграцій. Це означає, що схема таблиць, RLS-політики та зміни бази не відтворюються з цього репозиторію. Це не доводить, що міграцій немає поза репозиторієм, але локальний процес відновлення бази не зафіксований.

## 6. Перспективи, що випливають із проєкту

Це не вигадані функції, а напрямки, які логічно випливають із уже наявних меж коду:

1. **Уніфікувати обробку помилок serverless-запитів.** У daily reminders вже є один централізований flow відправлення push, тому перевірки Supabase можна зробити послідовними в цьому ж модулі.
2. **Зробити E2E частиною перевірки merge у `main`.** Наявні Playwright-тести вже запускаються на production preview, тому питання полягає в CI-тригері, а не в запровадженні нового інструмента.
3. **Синхронізувати README та аудити з автоматично отриманими метриками.** Розбіжність лічильників уже зафіксована цим аудитом.
4. **Додати відтворювану історію схеми Supabase.** У коді активно використовуються таблиці профілів, push-підписок, злучок, окролів, лікування та вакцинацій, але локальних міграцій немає.
5. **Розширити браузерний матричний тест після стабілізації основного flow.** Найближча підтверджена прогалина — mobile viewport, бо відповідний Playwright-проєкт уже передбачений коментарем у конфігурації.
6. **Зменшити ручну підтримку великого каталогу сторінок.** У `src/pages` фактично 405 файлів, тому генерація перевірок route-to-page відповідності або автоматична перевірка sitemap має практичну цінність.

## 7. Що свідомо не оцінювалося

Без доступу до зовнішніх систем не робилися висновки про:

- фактичні RLS-політики та структуру production Supabase;
- реальну роботу Vercel functions у production;
- доставлення push на конкретні пристрої;
- Lighthouse, GTmetrix, HTTP-заголовки live-домену та uptime;
- коректність медичного/ветеринарного змісту;
- usability-оцінку всіх 405 сторінок;
- Android TWA та публікацію APK.

## 8. Підсумок

Поточний репозиторій технічно збирається і проходить наявні автоматичні перевірки. Архітектура має lazy routing, PWA, serverless push, ErrorBoundary, CI та виміряне coverage понад 90% statements для охопленого тестами коду.

Найважливіша підтверджена дія — оновити вразливу production-залежність `react-router`/`react-router-dom` і повторити повний набір перевірок. Далі за пріоритетом — не приховувати помилки запитів у daily reminders, запускати E2E після merge та синхронізувати документацію з фактичними метриками.
