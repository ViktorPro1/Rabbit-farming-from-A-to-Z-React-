# План виправлення моделі обліку

## Мета

Усунути перетин карантину й архіву, зафіксувати історію руху тварин, зробити продажі фінансово повними та захистити пов’язані записи від часткового збереження.

## 1. Розділити карантин і архів

У таблиці `rabbits` додати поле поточного стану:

```text
status: active | quarantine | archived
```

Правила відображення:

- Реєстр показує лише `status = active`.
- Карантин показує лише `status = quarantine`.
- Архів показує лише `status = archived`.

Поле `is_active` тимчасово зберегти для сумісності з наявним кодом. Після перенесення всіх перевірок на `status` його можна прибрати окремою погодженою зміною.

## 2. Зберігати історію подій тварини

Створити таблицю `animal_events`:

```text
id
rabbit_id
event_type
event_date
reason
source_table
notes
user_id
created_at
```

Типи подій:

- переведення в карантин;
- одужання та повернення до реєстру;
- забій;
- загибель;
- продаж;
- архівація;
- відновлення з архіву.

`rabbits.status` зберігає поточний стан, а `animal_events` — незмінну історію переходів.

## 3. Залишити відгодівлю груповим обліком

`fattening` має залишатися обліком партії або клітки, а не індивідуальною карткою кожного молодого кролика.

Для походження партії додати поля:

```text
source_type
source_litter_id
```

Так можна встановити, з якого окролу надійшла партія, не створюючи хибного індивідуального зв’язку між кожним кроленям і груповим записом.

## 4. Зробити продаж завершеною фінансовою операцією

Під час створення запису `sales` одразу вимагати:

- кількість за статтю;
- дату продажу;
- ціну;
- покупця, якщо потрібен.

Не створювати продаж без `price`. Так фінансова сторінка одразу показуватиме фактичний дохід, а не нульове значення до ручного редагування.

## 5. Виконувати пов’язані зміни транзакційно

Створити PostgreSQL RPC-функції в Supabase для операцій, які змінюють кілька таблиць. Операція має або повністю завершитися, або не змінити жодного запису.

Потрібні операції:

- переведення в карантин + оновлення `rabbits.status`;
- завершення карантину + повернення до реєстру або архівування;
- відлучення + створення або поповнення партії `fattening`;
- переведення тварини з відгодівлі на плем’я;
- продаж + зменшення залишку у `fattening` + створення `sales`.

## 6. Закріпити правила в базі даних

Додати зовнішні ключі, перевірки та політики доступу:

- `quarantine.rabbit_id` посилається на `rabbits.id`;
- `animal_events.rabbit_id` посилається на `rabbits.id`;
- `fattening.source_litter_id` посилається на `litters.id`;
- кількість самців, самиць і невизначених у відгодівлі не може бути від’ємною;
- для `status = archived` мають бути вказані `archive_reason` і `archive_date`;
- користувач бачить і змінює лише записи зі своїм `user_id`.

## 7. Не видаляти історичні записи напряму

Для тварин, злучок, окролів, продажів, витрат та інших фінансових записів додати м’яке видалення:

```text
deleted_at
deleted_by
delete_reason
```

Інтерфейс приховує скасовані записи зі звичайних списків, але історія та статистика залишаються перевірними.

## Порядок впровадження

1. Додати `status` і виправити розділення Реєстру, Карантину та Архіву.
2. Перевести продажі на обов’язкову ціну та одну транзакційну операцію.
3. Додати RPC для карантину, окролів, відгодівлі й продажів.
4. Додати `animal_events` та записувати в нього всі переходи станів.
5. Додати обмеження бази даних і політики доступу.
6. Впровадити м’яке видалення історичних даних.

## Очікуваний результат

Після впровадження кожна індивідуальна тварина матиме один однозначний поточний стан, карантин не змішуватиметься з архівом, продажі одразу потраплятимуть у фінансовий облік, а пов’язані дані не зможуть залишитися в частково оновленому стані.
