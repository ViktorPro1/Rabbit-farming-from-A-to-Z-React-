# Виконані виправлення обліку та безпеки

Документ підсумовує роботу, виконану у гілці `fix/accounting-sync`
на основі трьох документів («Аудит даних реєстру, карантину, архіву
та вибраковки», «Перевірка аудиту обліку», «План виправлення обліку»)
та додаткового ручного аудиту безпеки (RLS) по всіх таблицях Supabase.

Змерджено в `main` комітом `2296655` (fast-forward з `885591d`).

## Що перевірено

Прочитано й перевірено проти реального коду 16 сторінок додатку
(RabbitRegistry, RabbitEdit, Archive, Pedigree, CageSearch,
CalendarPage + calendarService, Matings, Paddocks, Fattening,
Quarantine, Statistics, MyVaccinations, MyTreatments,
DisinfectionLog, Weighing, FinancesPage, GrainRecipesHistory),
а також `Admin.tsx`, `pushNotifications.ts` і повний список RLS-
політик по всіх 24 таблицях бази.

## 1. Розсинхрон обліку між модулями

### Підтверджено з "Перевірки аудиту обліку"

- Карантин і Архів справді перетинались: тварина в АКТИВНОМУ
  карантині (`quarantine.is_active = true`) мала
  `rabbits.is_active = false` і тому потрапляла у видачу `Archive.tsx`
  поряд із реально вибулими тваринами.
- Продаж (`sales`) не завжди означає зафіксований дохід — запис
  створюється без `price`, ціна дописується окремо через
  `FinancesPage.handleSavePrice`; до цього фінансова агрегація
  повністю пропускає такий продаж (`if (!s.sold_at || !s.price) return`).
- Молодняк не має наскрізної індивідуальної картки: `litters` і
  `paddock_litters` — груповий підрахунок голів, без окремих `id`
  на кожну тварину. Виявлено і зворотний шлях: кнопка "На плем'я" у
  `Fattening.tsx` вставляє новий рядок у `rabbits`, але без
  `mother_id`/`father_id` і без посилання на партію-джерело.

### Виправлено

| Файл | Що змінено |
|---|---|
| `CageSearch.tsx` | Додано `sales` та вольєри (`paddocks`/`paddock_females`/`paddock_matings`/`paddock_litters`) в історію по клітці |
| `Statistics.tsx` | `paddock_litters` враховується в Народжено/Живих; вибуття іменних кроликів реєстру (`archive_reason`: died/slaughter/sold) враховується в Баланс поголів'я, без подвійного рахування з карантином |
| `RabbitRegistry.tsx` | Запит лічильника `paddock_females` — додано пропущений `.eq('user_id', ...)` |
| `Quarantine.tsx` | При результаті slaughter/died тепер пишеться `archive_reason` і `archive_date` в `rabbits` |
| `Archive.tsx` | Виключено з видачі кроликів, що зараз в активному карантині |

## 2. Безпека — Row Level Security

Перевірено весь `pg_policies` для 24 таблиць. Знайдено систематичний
патерн: політики з назвою, що має на увазі обмежений доступ, але з
`qual = true` (доступ фактично не обмежений жодним чином) —
у Postgres RLS кілька permissive-політик на одну команду
об'єднуються через OR, тому одна відкрита політика перекреслює всі
інші, навіть коректні.

### Знайдено й закрито

| Таблиця | Проблема | Виправлення |
|---|---|---|
| `rabbits`, `matings`, `litters`, `fattening`, `weighings` | SELECT `qual=true` — повний анонімний доступ до всіх рядків усіх користувачів | 5 RPC-функцій (`security definer`), що приймають конкретний `id` і повертають максимум один рядок |
| `profiles` | Політика "admins can read profiles" мала `qual=true` — читав будь-хто, не лише адміни | Замінено на реальну перевірку через `admins` |
| `invite_codes` | Дві зайві SELECT-політики з `qual=true` поряд з коректною admin-only — інвайт-гейт фактично не працював | Видалено зайві, лишено наявну коректну |

### Причина існування публічного доступу — легітимна

`RabbitPublic.tsx` і `FatteningPublic.tsx` — публічні сторінки для
QR-кодів на клітках, показують картку кролика/клітки без логіна.
Функціонал збережено повністю — обидва компоненти переведено з
прямих `.from(...).select(...)` на виклики нових RPC-функцій.

### Перевірено й підтверджено без проблем

- `push_subscriptions` (`pushNotifications.ts`): код не фільтрує по
  `user_id` у деяких запитах, але таблиця має коректну `ALL`-політику
  з `USING`+`WITH CHECK` (`auth.uid() = user_id`) — база сама
  блокує доступ до чужих рядків незалежно від коду фронтенду.
- `health_log`, `weight_log`: політики коректні, але жоден компонент
  у `src/` не читає й не пише в ці таблиці напряму (лише згадка в
  `Admin.tsx` для лічильника). Перевірено запитом `count(*)` —
  обидві таблиці порожні (0 рядків). Мертвий залишок старої версії
  модуля зважування, ризику немає.

## Оцінка "Плану виправлення обліку"

План (`status`-поле замість розрізнених прапорців, таблиця
`animal_events`, `source_litter_id` у Fattening, обов'язкова ціна
при продажу, транзакційні RPC, зовнішні ключі, м'яке видалення) —
архітектурно правильний напрямок для довгострокової стійкості,
особливо з огляду на плани зробити цей довідник спільним продуктом
для багатьох користувачів по всій Україні.

**Не впроваджено сьогодні.** Сьогоднішні виправлення — це патчі, що
закривають конкретні підтверджені розриви в поточній моделі даних;
вони не захищають від того, що та сама категорія помилки
(пропущена синхронізація статусу, відсутня транзакційність) з'явиться
знову в майбутньому коді. Перехід на `status`+`animal_events` варто
розглянути окремим етапом, до появи сторонніх користувачів, а не
паралельно з поточними патчами.

## Підсумок

Модель даних лишається такою, якою її описує оригінальний аудит:
кілька пов'язаних таблиць, не єдиний ledger. На сьогодні:

- усі підтверджені розсинхрони обліку між реєстром, карантином,
  вольєрами, відгодівлею й продажами — усунуто;
- усі знайдені відкриті RLS-політики — закрито, без втрати
  функціоналу QR-сторінок;
- усі 24 таблиці бази даних перевірено, жодної неперевіреної не
  лишилось.
