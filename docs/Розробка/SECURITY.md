# Безпека

## Змінні оточення

Клієнт Supabase у `src/lib/supabase.ts` потребує двох змінних:

```env
VITE_SUPABASE_URL=
VITE_SUPABASE_ANON_KEY=
```

Почніть із `.env.example`; `.env` та `.env.*` уже виключені з Git через `.gitignore`.

Префікс `VITE_` означає, що значення потрапляє до клієнтського збірника. Тому тут дозволений лише URL проєкту та публічний Supabase anon key. Не додавайте до `.env`, коду чи документації `service_role` key, паролі, токени доступу або приватні ключі.

## Supabase і доступ до даних

Застосунок виконує автентифікацію та операції з даними безпосередньо через `@supabase/supabase-js`. Захист даних має забезпечуватися в Supabase, а не приховуванням маршруту або кнопки у React.

- Для таблиць з даними користувачів застосовуйте Row Level Security та політики, що обмежують доступ власником запису.
- Перевіряйте права для адміністративних RPC і таблиць у Supabase окремо від UI.
- Не переносіть привілейовані операції у фронтенд і не використовуйте для них anon key.

## Сторонні з’єднання

У `vercel.json` задана Content Security Policy. Якщо додається зовнішній сервіс, спочатку визначте, для чого потрібні його домени, а потім мінімально доповніть відповідну директиву CSP (`connect-src`, `script-src` або іншу). Не послаблюйте політику широкими дозволами без необхідності.

Google Analytics завантажується компонентом `CookieConsent` лише після згоди на категорію `analytics`. Нові аналітичні інтеграції мають дотримуватися цього підходу.

## Повідомлення про проблему

Не додавайте чутливі дані до issue, комітів або публічних повідомлень. Якщо знайдено вразливість, передайте деталі власнику проєкту приватним каналом, а до виправлення не публікуйте інструкції з її відтворення.
