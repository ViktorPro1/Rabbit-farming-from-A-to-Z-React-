# CI

## Що це таке простими словами

Це основний "конвеєр перевірки якості" проєкту. Кожного разу, коли
хтось пушить код у `main` чи `feature/**`, або відкриває Pull Request
у `main`, GitHub автоматично запускає низку перевірок: лінтер, типи,
тести, білд і (для PR) end-to-end тести.

Якщо будь-яка перевірка провалиться — це видно одразу в PR, і мерджити
"поламаний" код стає складніше, бо помилку видно ще до того, як хтось
її побачить у проді.

## Коли він запускається

- При push у `main` або в будь-яку гілку `feature/...`.
- При Pull Request у `main`.

Ще є важлива штука — блок `concurrency`: якщо в той самий PR прилетів
новий push, попередній (застарілий) запуск CI автоматично скасовується.
Це економить час і ресурси — немає сенсу довіряти перевірку старого
коду, коли вже є новіший.

## З яких завдань (jobs) складається

1. **Lint** — перевіряє стиль коду через ESLint (`npm run lint`).
2. **Typecheck** — окремо і швидко перевіряє типи TypeScript
   (`tsc -b --noEmit`), без повного білду. Це зроблено спеціально, щоб
   не чекати на build-джобу, а отримати результат швидше.
3. **Tests** — запускає тести з підрахунком покриття
   (`npm run test -- --coverage`) і завантажує звіт про покриття як
   артефакт (зберігається 14 днів), навіть якщо тести впали
   (`if: always()`).
4. **Build** — збирає прод-білд (`npm run build`), використовуючи
   секрети `VITE_SUPABASE_URL` і `VITE_SUPABASE_ANON_KEY`. Запускається
   тільки після успіху lint, typecheck і test (`needs: [...]`).
   Готовий білд (`dist/`) зберігається як артефакт на 7 днів.
5. **E2E (Playwright)** — запускається **тільки для Pull Request**
   (не для звичайного push). Збирає білд ще раз, встановлює браузер
   Chromium (з кешуванням, щоб не качати його щоразу заново) і прогонає
   end-to-end тести через Playwright. Звіт зберігається як артефакт
   на 7 днів, навіть якщо тести впали.

## Навіщо це потрібно

Це стандартний CI-конвеєр, який захищає `main` від поламаного коду:
перш ніж зміни потраплять у гілку, автоматично перевіряється стиль,
типи, логіка (тести) і те, що проєкт взагалі збирається. Для PR
додатково прогоняються e2e-тести, які імітують реальну поведінку
користувача в браузері.
