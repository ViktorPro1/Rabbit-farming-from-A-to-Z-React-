# Developer guide

Цей документ описує процес розробки, запуску, тестування, CI та релізів для проєкту **Кролівництво від А до Я**.

## 1. Мета

Мета цього гіда — зібрати ключові кроки для нових розробників і зробити роботу однорідною:

- швидкий старт у локальному середовищі;
- запуск lint, build, тестів;
- базовий CI-процес;
- порядок підготовки релізу;
- правила роботи з компонентами.

## 2. Локальна розробка

### 2.1 Клонування репозиторію

```bash
git clone <repo-url>
cd "Кролівництво від А до Я"
```

### 2.2 Встановлення залежностей

```bash
npm install
```

### 2.3 Запуск дев-сервера

```bash
npm run dev
```

Відкрийте у браузері `http://localhost:5173`.

### 2.4 Попередній перегляд production-білду

```bash
npm run preview
```

### 2.5 Змінні оточення

Локально створіть `.env` або `.env.local` зі значеннями:

```env
VITE_SUPABASE_URL=https://your-supabase-project-url
VITE_SUPABASE_ANON_KEY=your-supabase-anon-key
```

> Не зберігайте секретні ключі у git. `.env*` має бути в `.gitignore`.

## 3. Основні npm-скрипти

### Розробка

- `npm run dev` — запускає Vite у режимі розробки.
- `npm run preview` — запускає локальний сервер для перевірки production-білду.

### Перевірка та збірка

- `npm run lint` — запускає ESLint по всьому репозиторію.
- `npm test` — виконує всі існуючі тести через Vitest.
- `npm run build` — генерує sitemap, компілює TypeScript, виконує Vite build та пререндеринг.

## 4. CI-процес (рекомендований)

### 4.1 Що перевіряє CI

CI має запускати мінімальні кроки при push/PR:

1. `npm ci`
2. `npm run lint`
3. `npm test`
4. `npm run build`

Якщо хочете, додайте кроки для перевірки type coverage та security scan.

### 4.2 Приклад GitHub Actions

```yaml
name: CI

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  build:
    runs-on: ubuntu-latest

    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v5
        with:
          node-version: 20
          cache: "npm"
      - run: npm ci
      - run: npm run lint
      - run: npm test
      - run: npm run build
```

> Якщо тестам потрібні змінні оточення, збережіть їх у Secrets (`VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`).

## 5. Релізний процес

### 5.1 Підготовка

1. Оновіть ветку з останнім `main`.
2. Запустіть `npm run lint`.
3. Запустіть `npm test`.
4. Запустіть `npm run build`.

### 5.2 Перевірка

Переконайтеся, що:

- `dist/` створений;
- `public/sitemap.xml` згенеровано;
- в `dist/` є `sw.js` та статичні файли;
- build завершився без помилок.

### 5.3 Деплой

Для Vercel:

- Build command: `npm run build`
- Output directory: `dist`
- Додайте Secrets: `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`

Якщо деплоїте на статичний хост:

- Завантажуйте вміст каталогу `dist/`.
- Переконайтеся, що fallback SPA обробляється сервером.

### 5.4 Чекліст релізу

- [ ] Код пройшов lint.
- [ ] Тести пройшли.
- [ ] Build пройшов.
- [ ] Sitemap згенеровано.
- [ ] `dist/` перевірено.
- [ ] У PR є опис змін.
- [ ] Результати CI зелені.

## 6. Створення та оновлення компонентів

### 6.1 Іменування

- Файли компонентів: `PascalCase`, наприклад `Header.tsx`.
- Хуки: `camelCase`, наприклад `usePublicPresence.ts`.
- CSS: `kebab-case`, наприклад `AssistantPromo.css`.

### 6.2 Розмір та складність

- Компонент повинен бути компактним.
- Якщо компонент росте, винесіть частини в підкомпоненти.
- Розділяйте логіку та UI.
- Уникайте великих сторінок з денною логікою у одному файлі.

### 6.3 Пропси та типи

- Типізуйте `props` через `interface` або `type`.
- Не використовуйте `any`, якщо можна визначити конкретний тип.
- Уникайте `props`-drilling, коли це можливо, але не додавайте передчасну складність.

### 6.4 Взаємодія з роутами

- Нові сторінки додавайте до `src/pages`.
- Маршрути реєструйте в `src/routes/groups/*`.
- `src/routes/AppRoutes.tsx` агрегає всі групи маршрутів.
- Використовуйте `lazy()` для великих сторінок, щоб зменшити початковий JS.

### 6.5 Обробка помилок

- Для глобальних помилок використовуйте `src/components/ErrorBoundary/ErrorBoundary.tsx`.
- Внутрішні компоненти можуть мати власні boundary, якщо вони містять складну асинхронну логіку.
- Логування помилок має бути видимим у консолі та, за потреби, відправленим до сервісу логування.

## 7. Рекомендовані правила

- Запускайте `npm run lint` перед PR.
- Пишіть тести для нових компонентів та логіки.
- Стежте за розмірами файлів у `dist/` після великих змін.
- Додайте коментарі до нетривіальних рішень при необхідності.
- Скористайтеся наявними документами:
  - `docs/STYLE_GUIDE.md`
  - `docs/ENVIRONMENT.md`
  - `docs/DEPLOYMENT.md`
  - `docs/STRUCTURE.md`

## 8. Додаткова інформація

### Де шукати відповіді

- `src/App.tsx` — root-компонент, auth, offline, splash, ErrorBoundary.
- `src/routes/AppRoutes.tsx` — центральний роутинг.
- `src/lib/supabase.ts` — Supabase-конфігурація.
- `src/hooks` — кастомні хуки.
- `src/components` — загальні UI-компоненти.

### Що важливо пам’ятати

- Це контентний проєкт з великою кількістю сторінок.
- Архітектура має зберігати зрозумілу структуру, щоб нові сторінки не ускладнювали підтримку.
- CI має виконувати базову перевірку якості перед релізом.
- Документація повинна зростати разом з кодом.
